## 1. ملخص تنفيذي

### نقاط القوة الحالية

المشروع في حالة جيدة أكثر مما يبدو من حجمه. تحققت من الأمور التالية فعليًا في الكود:

- **كل المنافذ محلية**: لا توجد أي خدمة تستمع على `0.0.0.0`. جميع المستمعين
  (FastCGI، HTTP/HTTPS، DNS، SMTP، Dumps، وكل خدمات قواعد البيانات) مقيّدون
  بـ `127.0.0.1`، وPHP-FPM يستخدم `listen.allowed_clients = 127.0.0.1`.
- **حماية من Path Traversal والروابط**: المنصتان تطبّعان المسار وتمنعان `..`
  المشفّر والصريح، وتحلان symlink/junction وتتحققان من الاحتواء داخل جذر
  الموقع. Windows يعيد التحقق من المسار النهائي عبر handle الملف المفتوح.
- **تحقق من سلامة التنزيلات على Windows**: PHP وNode وComposer وXdebug وكل
  الخدمات تتحقق من SHA-256 قبل التثبيت.
- **مساحة اختبارات محترمة**: 151 اختبار XCTest على macOS و~100 تحقق تعاقدي على
  Windows، مع بوابة حقيقية لإنشاء وتشغيل مشروع Laravel.
- **سياسة PHP موحّدة**: التثبيتات الجديدة على المنصتين تعرض وتقبل PHP
  `8.0–8.5` فقط. تبقى دورة أقدم مثل `7.4` ظاهرة وقابلة للاختيار إذا كانت مثبتة
  فعليًا، من دون عرض زر تثبيت أو تحديث غير قابل للتنفيذ.
- **نظافة المستودع**: لا توجد ملفات بناء مُتتبعة في Git ولا `.DS_Store`.

> النواة المشتركة `Core/` (413 سطر C++) تُستخدم من Windows فقط عبر
> استدعاء `herdme-core.exe` كعملية فرعية. **macOS لا يبنيها ولا يستدعيها ولا

## 2. تحسينات الباك اند

### 2.1 الأمان

#### [حرجة] B-1: تنزيل Node.js بدون تحقق من البصمة (macOS)

> **تم التنفيذ:** يُجلب `SHASUMS256.txt` الرسمي ويُختار السطر المطابق لاسم
> الأرشيف حرفيًا، ثم تُقارن SHA-256 قبل فك الضغط مع فشل مغلق واختبارات ثابتة.

`HerdMe/Services/RuntimeInstaller.swift:157-165` — يُنزّل الأرشيف ويفكّه مباشرة:

```swift
let downloadURL = URL(string: "https://nodejs.org/dist/\(release.version)/\(archiveName)")!
let (temporaryArchive, downloadResponse) = try await URLSession.shared.download(from: downloadURL)
guard (downloadResponse as? HTTPURLResponse)?.statusCode == 200 else {
    throw RuntimeInstallationError.invalidResponse
}
try unpack(archive: temporaryArchive, into: staging)   // ← لا تحقق من البصمة
```

المفارقة أن نسخة Windows في `NodeRuntimeInstaller.cs:190` **تتحقق** فعلًا
(`await DownloadAndVerifyAsync(...)`). أي أن macOS أضعف أمنيًا من Windows في نفس الميزة.

**الإصلاح**: تنزيل `SHASUMS256.txt` من نفس مجلد الإصدار، والتحقق من بصمة
الأرشيف قبل `unpack`، مع الفشل المُغلق (fail-closed) عند عدم التطابق. ويُفضّل
التحقق من `SHASUMS256.txt.sig` بمفتاح Node.js الرسمي.

#### [عالية] B-2: Xdebug من PECL بدون تحقق

> **تم التنفيذ:** انتقل macOS إلى صفحة تنزيل Xdebug الرسمية، ويستخرج منها
> الإصدار ورابط HTTPS وبصمة SHA-256 ذات 64 خانة. تُفحص البصمة وقائمة مسارات
> الأرشيف قبل الفك، مع رفض المسارات المطلقة و`..` وحد أقصى 20,000 مدخل.

`HerdMe/Services/XdebugManager.swift:190-217` — يُنزّل `.tgz` من `pecl.php.net`،
يُترجمه، ويُحمّله كـ `zend_extension`. رقم الإصدار يُتحقق منه بـ regex لكن محتوى
الأرشيف موثوق بالكامل. نسخة Windows تستخدم بصمة SHA-256 من GitHub Releases.

**الإصلاح**: مواءمة macOS مع نموذج Windows (أرشيفات GitHub مع SHA-256)، أو
التحقق من بصمات PECL المنشورة.

#### [عالية] B-3: تحديثات التطبيق بدون توقيع

> **تم التنفيذ في طبقة التحقق:** يستخدم macOS وWindows غلافًا موقعًا بـ
> ECDSA P-256/SHA-256 فوق بايتات البيان الأصلية. البيانات الخارجية غير الموقعة
> أو المعدلة تُرفض، ومتغيرات البيئة محصورة في Debug. أضيفت أداتا توقيع
> `scripts/sign-update-manifest.sh` و`scripts/sign-update-manifest.ps1` ودليل
> `docs/RELEASING.md`. أضيفت روابط تنزيل GitHub Release المنفصلة للمنصتين،
> ومفتاح التحقق العام ورابط التغذية، ونجح توقيع التغذية والتحقق منها محليًا.
> أصبحت مقارنة إصدارات التطبيق والأدوات تطبق أسبقية SemVer نفسها على المنصتين:
> الإصدار المستقر يتقدم على prerelease، والمعرّفات الرقمية مثل `beta.10`
> تتقدم على `beta.2`، وbuild metadata لا يصنع تحديثًا زائفًا. ترفض تطبيقات
> وسكربتات التوقيع معًا صيغ SemVer غير الصالحة قبل النشر.
> أضيف أيضًا Workflow الإصدار العام؛ ويبقى I-22 مفتوحًا حتى تُضبط أسرار GitHub
> وشهادات المنصتين ويُنشَر أول إصدار موقّع فعليًا.

`HerdMe/Services/AppUpdateManager.swift:39-46` — `HERDME_UPDATE_FEED_URL` يسمح
بتوجيه التطبيق لأي عنوان، والبيان (manifest) يُفكّ ترميزه من JSON بدون أي تحقق من
الأصالة، ثم يُفتح رابط التنزيل عبر `NSWorkspace`. نفس المشكلة على Windows
(`AppUpdateManager.cs:63-104`).

**الإصلاح**: تجاهل متغير البيئة في إصدارات Release، توقيع البيانات بـ Ed25519
والتحقق قبل العرض، أو الانتقال إلى Sparkle على macOS.

#### [منفذ برمجيًا، القبول الموقّع متبقٍ] B-4: إزالة API الصلاحيات المهجورة

> **تم التنفيذ في المصدر والاختبارات:** حُذف
> `PrivilegedCommandRunner.swift` وكل استخدام لـ
> `AuthorizationExecuteWithPrivileges`. يسجل HerdMe الآن LaunchDaemon ثابتًا
> ومضمّنًا عبر `SMAppService.daemon(plistName:)`، ولا يوفّر قناة shell أو XPC
> عامة لتنفيذ أوامر بصلاحية root. يقرأ المساعد ملف routing محدود الحقول، يتحقق
> منه بصرامة، ينشئ resolver ذريًا، يحجز منافذ loopback فقط، ثم يشغّل عامل الشبكة
> بهوية المستخدم الحالي.
>
> ترحيل المساعد القديم أصبح transaction قابلًا للاسترجاع: تبقى ملفاته سليمة حتى
> ينجح حجز 53/80/443 وإسقاط الصلاحيات، وتُعاد خدمة launchd القديمة عند الفشل.
> تستخدم سياسة `KeepAlive/SuccessfulExit=false` خروج rollback الناجح لمنع حلقة
> توقف وإعادة تشغيل. يغطي اختبار ديناميكي معزول مساري النجاح والفشل، ويتحقق
> التغليف من manifest ومعماريتي المساعد وتوقيعه وتطابق Team ID في الوضع العام.
> توثيق الشهادة انتقل كذلك إلى Security.framework في نطاق المستخدم.

**بوابة القبول المتبقية**: تشغيل تسجيل الخدمة والترحيل وتوثيق CA من حزمة
Developer ID منوترة على تثبيت macOS نظيف، ثم إثبات HTTP وHTTPS وDNS وإعادة
التشغيل. لا يمكن اعتبار حزمة ad-hoc دليلاً على موافقة Service Management أو
Gatekeeper.

#### [تم] B-5: SMTP يعلن حدًا ولا يفرضه

> **تم التنفيذ:** يخزن macOS بحد أقصى 50MB فقط لكل رسالة، ويُرجع `552` بعد
> نهاية DATA عند التجاوز، ويحد السطر غير المكتمل بـ1MB. يفك dot-stuffing بعد
> قبول الحجم فقط، وتغطي الاختبارات التجاوز وإعادة الضبط.

`HerdMe/Services/SMTPServer.swift:125` يُعلن `250 SIZE 52428800`، لكن
`SMTPServer.swift:118` يُضيف الأسطر بلا حدّ:

```swift
} else {
    dataLines.append(line)   // ← بلا أي عدّ للبايتات
}
```

نسخة Windows (`MailCaptureService.cs:206`) تفرض الحد بشكل صحيح.

**الإصلاح**: تتبّع عدد البايتات التراكمي والرفض بـ `552` عند تجاوز 50MB، وتحديد
سقف لنمو `buffer` داخل `receive()`.

#### [تم] B-6: حدود مفقودة في مُحلّلات الإدخال غير الموثوق

> **تم التنفيذ:** فُرض 4MB على إدخال PHP serialized وكل اتصال dumps، و10,000
> عنصر وعمق 32 على المحلل، وعمق 16 على العرض النصي. تُغلق جلسة dumps فور تجاوز
> الحد، وتغطي الاختبارات الحجم والعدد والعمق.

- `PHPSerializationParser.swift:108-130`: يقرأ `count` من الحمولة ويكرّر بلا سقف،
  و`rendered(depth:)` بلا حدّ عمق → استهلاك ذاكرة/تعمّق مكدس من حمولة خبيثة.
- `DumpCaptureServer.swift:76-97`: `buffer` يتراكم بلا سقف إجمالي (فقط كل قراءة
  محدودة بـ 1MB).

**الإصلاح**: سقوف صريحة (10,000 عنصر، عمق 32، 4MB لكل اتصال) ورفض الاتصال عند التجاوز.

#### [تم] B-7: عرض HTML للبريد بـ `unsafe-inline`

> **تم التنفيذ:** أزيل `unsafe-inline`، وأصبحت CSP تسمح فقط بورقة نمط HerdMe
> ذات بصمة SHA-256 وتمنع النماذج والإطارات والكائنات والخطوط والمصادر الخارجية.
> JavaScript معطل، وmacOS يلغي كل تنقل خارج المستند، بينما يلغي Windows أيضًا
> النوافذ الجديدة والتنزيلات. حُدت المعاينة إلى 4MB على المنصتين.

`MailMIMEParser.swift:59-67` يُدرج HTML الخام داخل `<body>`، وCSP يسمح بـ
`style-src 'unsafe-inline'`. JavaScript مُعطّل (جيد، `MailHTMLPreview.swift:11`)
لكن يبقى تسريب عبر CSS وإعادة تشكيل الواجهة.

**الإصلاح**: تنقية HTML بقائمة سماح للعناصر والسمات قبل الإدراج، وتضييق CSS
إلى `'none'` أو تقديم النص العادي افتراضيًا.

#### [تم] B-8: بيانات اعتماد ثابتة ومكشوفة

> **تم التنفيذ:** ينشئ HerdMe لكل نسخة خدمة اسم مستخدم فريدًا وسرًا عشوائيًا
> بقوة 256-bit ويحفظهما في Keychain على macOS وWindows Credential Manager.
> تستخدم MinIO وRustFS وTypesense السر عند التشغيل، وتستخدم MySQL وMariaDB
> وPostgreSQL الاعتماد نفسه في المحرك و`.env` وTablePlus. يبدأ PostgreSQL الجديد
> مباشرة بـ SCRAM، وتُؤمّن MySQL/MariaDB قبل إعلان الخدمة Running.

التركيبات القديمة ذات `trust` أو root بلا كلمة مرور تُرحّل عند أول تشغيل. لا
تُكتب علامة `.herdme-auth-v1` إلا بعد نجاح الدخول بالسر وفشل الدخول بدونه.
يستبدل ترحيل PostgreSQL قواعد `trust` ذريًا ويسترجع `pg_hba.conf` السابق إذا
فشل التحقق؛ ولا يحذف أي مسار بيانات عند الفشل. تُرسل أوامر SQL التي تحتوي السر
عبر stdin بدل معاملات العملية، وتعمل أدوات Windows مع `CreateNoWindow=true`.
تغطي العقود صياغة قواعد المصادقة وتطابق `.env` وTablePlus، ونجحت بوابة macOS
الحية على MySQL وMariaDB الحقيقيين مع إثبات رفض الدخول بلا سر.

#### [تم] B-9: مفتاح CA الخاص على القرص

> **تم التنفيذ:** على macOS يُحفظ مفتاح CA الخاص وكلمة مرور PKCS#12 العشوائية
> في Data Protection Keychain بسياسة `AfterFirstUnlockThisDeviceOnly`. يتحقق
> الترحيل من تطابق المفتاح القديم مع شهادة CA قبل حفظه، ثم يحذف المفتاح وملفات
> leaf/CSR الخام، ويستخدم staging بصلاحية `0700` وstdin عند استدعاء OpenSSL.
> تحاول الحزم الموقعة محليًا Data Protection أولًا، ثم تستخدم login Keychain
> فقط عند `errSecMissingEntitlement` لأن التوقيع ad-hoc لا يملك TeamIdentifier.
> عند تشغيل حزمة موقعة رسميًا يُنقل السر إلى Data Protection تلقائيًا، ولا تُحذف
> نسخة login إلا بعد نجاح الكتابة المحمية. تغطي الاختبارات حالتي اختلاف نتيجة
> القراءة (`errSecMissingEntitlement` أو `errSecItemNotFound`) مع فشل الترحيل
> بالخطأ نفسه؛ وقد نجح اختبار Release حي عبر HTTP وHTTPS بلا منفذ عام ظاهر.
> على Windows انتقلت كلمات مرور `authority.pfx` و`server.pfx` إلى Credential
> Manager. اسم كل سر مرتبط ببصمة SHA-256 لمحتوى PFX لمنع عدم التطابق عند انقطاع
> الاستبدال، وتُحذف ملفات `.password` القديمة فقط بعد حفظ السر وإعادة قراءته
> بنجاح، وتُحمّل المفاتيح عبر `EphemeralKeySet`. تغطي اختبارات macOS وعقود
> Windows العابرة للمنصات الترحيل وثبات CA وترتيب الحذف الآمن.

كانت الملاحظة الأصلية أن `LocalCertificateManager.swift` و
`WindowsCertificateManager.cs` يتركان مادة المفتاح قابلة للاسترجاع من ملفات
المستخدم وحدها. لم يعد أي مفتاح خام يبقى على macOS، ولا تكفي ملفات PFX على
Windows لفك المفتاح من دون السر المحمي في Credential Manager.

**الإصلاح**: تخزين المفتاح في Keychain / User store مع تقوية ACL.

#### [تم] B-10: فكّ الأرشيف بدون تحقق من المسارات

> **تم التنفيذ:** يفحص macOS قائمتي أسماء وأنواع/أحجام مدخلات tar قبل الفك،

#### [تم] B-11: تجميد محتمل في كل استدعاءات `Process`

> **تم التنفيذ:** انتقلت أوامر الفحص والتثبيت والإنشاء إلى `ProcessRunner`
> المشترك، الذي يصرف stdout وstderr بالتوازي، ويفرض مهلة وسقف التقاط 16MB،
> ويدعم الإلغاء وإنهاء شجرة العملية. بقي استخدام `Process` المباشر فقط لعمليات
> الخدمات وPHP-FPM طويلة العمر التي لا تجمع مخرجاتها في أنبوب ممتلئ.

نمط متكرر في **14 موضعًا موزّعة على 10 ملفات** (تحققت بالعدّ:
`ProjectCreator` 4، `RuntimeInstaller` 2، وموضع واحد في كلٍّ من
`ServiceProcessManager`، `XdebugManager`، `PHPRuntimeValidator`، `PHPFPMManager`،
`DomainResolverManager`، `LocalCertificateManager`، `RuntimeInspector`، `AppModel`):

```swift
try process.run()
let data = pipe.fileHandleForReading.readDataToEndOfFile()
process.waitUntilExit()
```

إذا تجاوز مخرج العملية الابنة سعة الأنبوب (~64KB) قبل أن يقرأه الأب، تتوقف
الابنة عند الكتابة ويتوقف الأب عند القراءة — تجميد كلاسيكي. هذا يمسّ
`brew install` و`laravel new` و`npm install` و`composer global require` — وكلها
تُنتج مخرجات كبيرة جدًا.

**الإصلاح**: نوع مشترك `ProcessRunner` يقرأ stdout/stderr بشكل غير متزامن على
طابور خلفي أثناء الانتظار، مع مهلة زمنية، وإلغاء (cancellation)، وبثّ المخرجات
للسجل. هذا يغلق B-11 ويجعل العمليات قابلة للاختبار؛ عولج B-13 بقفل دورة
الحياة، بينما يعالج حد التطبيق المركزي استثناءات أحداث B-15 القابلة للاسترداد.

#### [تم] B-12: تسريب جلسات في SMTP و Dumps

> **تم التنفيذ:** تمرر خوادم SMTP وDumps الآن `onStop` لكل جلسة وتحذفها من
> القاموس المحمي بقفل عند الإغلاق أو الفشل أو الإلغاء، مع بقاء `stop()` آمنًا
> عند تكرار نداء الإزالة.

`SMTPServer.swift:47-51` و`DumpCaptureServer.swift:46-50` يُضيفان الجلسة إلى
المصفوفة ولا يحذفانها عند انتهائها (تُفرَّغ فقط في `stop()`). النمط الصحيح
موجود بالفعل في `LocalFastCGIGateway` و`LocalHTTPProxy` عبر `onStop`.

**الإصلاح**: تمرير `onStop` لحذف الجلسة من المصفوفة.

#### [تم] B-13: `@unchecked Sendable` مع أقفال غير كافية

> **تم التنفيذ:** أصبحت انتقالات `state` و`start` و`stop` و`consoleURL`
> متسلسلة بقفل دورة حياة واحد، مع قفل منفصل للخرائط الداخلية. يغطي اختبار حي

`ServiceProcessManager.swift:46` مُعلَّم `@unchecked Sendable`، و`state(for:)`
يقرأ ويكتب `adoptedProcessIDs` عبر دورات قفل/فتح متعددة → تعارض ممكن بين

القفل لكنه يستدعي مساعدات sysctl خارجه.

**الإصلاح**: تحويله إلى `actor`، أو الإمساك بالقفل لكامل الانتقال بين الحالات.

#### [عالية] B-14: حالة بيئة قديمة (stale)

> **تم التنفيذ:** الصحة الآن تتطلب عملية PHP-FPM حية واتصال TCP ناجح لكل
> runtime ولكل بوابة FastCGI ووكيل HTTP وHTTPS. حالة البدء الجزئية تُنظف قبل
> إعادة البناء، ويستعيد `AppModel` البيئة تلقائيًا عند اكتشاف انهيار وكان
> التشغيل التلقائي مفعّلًا. كما يزيل بدء البيئة مجلد `Runtime/routers` القديم
> الذي لم يعد مستخدمًا بعد الانتقال إلى FastCGI المباشر، حتى لا تبقى مسارات
> مشاريع محذوفة على القرص؛ ويغطي الاختبار بقاء بقية ملفات `Runtime` دون تغيير.

`LocalEnvironmentEngine.swift:43-45` يعيد المنافذ مباشرة إذا كان `isRunning`
صحيحًا، بدون التحقق من أن البوابات والوكيل ما زالوا أحياء. انهيار PHP-FPM يترك
قاموس `gateways` قديمًا ومنافذ خاطئة.

**الإصلاح**: فحص صحة (health check) للاتصال بـ FPM وحالة المستمعين قبل الإرجاع
المبكر، وإعادة البناء عند الفشل.

#### [تم برمجياً] B-15: `async void` منتشر على Windows

> **تم التنفيذ في الكود:** يشترك `App` في حد `UnhandledException` مركزي فور
> التهيئة. الاستثناء القابل للاسترداد يُعلّم `Handled`، ويُكتب كاملاً في
> `Log/unhandled.log` ذي التدوير المحدود، وتظهر رسالة واحدة للمستخدم مع منع

> `async void` لأنها توقيعات أحداث XAML، بينما تختبر عقود C# سياسة الاسترداد
> والنص الاحتياطي. يلزم تشغيل WinUI فعلياً لإغلاق بوابة القبول الأصلية.

معالجات الأحداث في `SitesPage.xaml.cs` (الأسطر 46، 53، 102، …)،
`ServicesPage.xaml.cs:25-172`، `GeneralPage.xaml.cs:42-258`،

#### [تم] B-16: `.Result` على خيط الواجهة

#### [تم] B-17: حلقات انتظار حاجزة

> **تم التنفيذ:** أصبحت جاهزية الخدمات وPHP-FPM وترحيل مصادقة قواعد البيانات
> وإنهاء العمليات تستخدم انتظارًا غير حاجز قابلًا للإلغاء بمهل صريحة. تسلسل
> العمليات محمي ببوابة async ولا يُمسك أي `NSLock` عبر `await`. عند طلب إنهاء
> HerdMe يعيد AppKit نتيجة `terminateLater` ثم يوافق على الإنهاء بعد توقف

`usleep` لمدة 1–3 ثوانٍ لكل عملية بدء/إيقاف، مما يحجز خيوط `Task.detached`.

**الإصلاح**: انتظار غير متزامن بـ `Task.sleep` مع تراجع تدريجي (backoff) وفحص

#### [تم] B-18: `HttpClient` بلا مهلة زمنية

**الإصلاح**: `Timeout` صريح + Polly لإعادة المحاولة مع تراجع تدريجي.

**الحالة:** تستخدم تنزيلات PHP وNode وComposer وXdebug والخدمات مصنعًا موحدًا
بمهلة صريحة قدرها 10 دقائق وUser-Agent ثابت. مدير تحديث التطبيق يحتفظ بمهلته
الأقصر (60 ثانية). يبقى التراجع التدريجي تحسينًا منفصلًا.

#### [تم] B-19: غياب الإلغاء في العمليات الطويلة

> **تم التنفيذ:** معالجا إنشاء Laravel على macOS وWindows يمرران الإلغاء حتى
> أوامر Laravel وComposer وnpm وGit. يُقتل الأب وكل عملياته التابعة عند الإلغاء،

**الإصلاح**: `CancellationToken` كامل المسار، `process.terminate()` عند الإلغاء،
وتنظيف المجلد الجزئي.

### 3.2 أداء SwiftUI

#### [تم] F-5: `LogsView` أسوأ نقطة أداء في التطبيق

**الحالة:** أصبح المؤقت يطلق فحص metadata خفيفًا في الخلفية، ولا يُعاد تحميل
المحتوى إلا عند تغير الحجم أو وقت التعديل. تُلغى مهمة القراءة القديمة عند
تغيير الملف أو مغادرة الصفحة، ولا تُقرأ حتى 4MB على `MainActor`.

`LogsView.swift:13,41-43` — مؤقت كل ثانية على `.main`:

```swift
private let refreshTimer = Timer.publish(every: 1, on: .main, in: .common).autoconnect()
...
.onReceive(refreshTimer) { _ in
    if autoScroll { reloadFiles() }
}
```

إلى `@State content`. ثم `displayedContent` (سطر 23-28) يُقسّم ويُرشّح النص
الكامل في كل تكة وكل ضغطة مفتاح — O(n) لكل تحديث.

الفروق فقط، فهرسة بالأسطر للبحث، `LazyVStack` مع نطاق مرئي، وتأخير البحث 200ms.

### 5.5 سلسلة توريد الطرف الثالث

Windows نموذجه قوي: SHA-256 لكل شيء (PHP، Node، Composer، Xdebug، كل الخدمات)،
مع استثناءين مُوثَّقين بأمانة (MySQL بـ MD5 من كشط HTML، PostgreSQL ببصمة مثبّتة).

macOS نموذجه مختلف تمامًا وغير موثّق:

| المكوّن | المصدر | التحقق |
|---------|--------|--------|
| PHP | Homebrew (`shivammathur/php`) | قائمة سماح للصيغ، **لا بصمة** |
| Node | `nodejs.org` | SHA-256 من `SHASUMS256.txt` الرسمي قبل الفك ✅ |
| Composer | تنزيل مباشر | SHA-384 ✅ |
| الخدمات | صيغ Homebrew | تحليل `brew info`، لا بصمة للثنائي |
| Xdebug | `xdebug.org` | SHA-256 من صفحة التنزيل الرسمية + تدقيق مسارات الأرشيف ✅ |

**الإصلاح**: إضافة قسم macOS إلى `docs/THIRD_PARTY.md` يشرح نموذج ثقة Homebrew
وتثبيت الصيغ، وإصلاح B-1 وB-2 لمواءمة مستوى الأمان مع Windows.
